# FA Server 项目阶段总结与周报

> 报告日期：2026-07-27  
> 报告范围：基于当前代码、接口文档、提交记录及自动化测试结果整理

## 1. 执行摘要

FA Server 已完成文件夹级图像数据处理服务的主体建设，当前已打通以下核心链路：

```text
远端数据产生
    -> rsync 增量同步
    -> RAW 转 BMP 与业务重命名
    -> SQLite 任务记账
    -> 超分辨批量处理
    -> 结果状态查询
    -> 历史数据定期清理
```

项目已形成统一 Flask API、API Key 认证、OpenAPI 定义、离线 Swagger 页面、后台任务执行器和文件夹级 SQLite 任务数据库。截至报告日期，当前代码通过 57 项自动化测试。

现阶段可定义为：

> 业务流程和工程框架已基本完成，具备继续开展生产联调的条件；真实 RAW/XML 规则、生产 Unet 模型、性能容量及正式部署方案仍需进一步验证和收口。

当前测试结果只能证明代码层的功能和主要状态转换符合预期，不能等同于生产算法效果、处理性能或生产稳定性已经完成验收。

## 2. 项目背景

业务现场存在持续产生的大批量图像数据，需要从局域网内的远端服务器同步到处理服务器，并依次完成格式转换、业务命名和超分辨增强。

如果直接通过人工脚本分别执行各环节，将面临以下问题：

- 数据是否同步完整缺少统一判断依据。
- 转码、重命名和超分辨之间缺少可靠的处理顺序。
- 任务中断后难以确认已处理、未处理和失败的数据。
- 模型重复加载会增加资源消耗和任务启动时间。
- 历史任务目录持续累积，可能造成磁盘空间风险。
- 不同服务器和操作系统的路径差异增加部署和排查成本。

FA Server 的建设目标不是重新实现生产算法，而是建立稳定的任务编排、状态管理和算法对接框架，使同步与图像处理过程可以通过标准接口统一管理。

## 3. 业务目标与实际价值

### 3.1 业务目标

1. 以 `folder_name` 作为业务任务标识，统一管理一个文件夹内的数据生命周期。
2. 通过 rsync 周期性拉取增量数据，并支持目标目录尚未创建的等待场景。
3. 根据 XML manifest 判断预计数据量和任务完成情况。
4. 对 RAW 文件执行转码和业务重命名，并只保留最终有效产物。
5. 以批次方式执行超分辨处理，并避免同一模型重复加载。
6. 通过 SQLite 持久化任务和图片状态，支持接口查询和故障定位。
7. 定期清理历史任务目录，控制本地存储规模。

### 3.2 实际价值

| 价值方向 | 具体体现 |
| --- | --- |
| 流程标准化 | 将同步、转码、重命名和超分辨统一为可调用、可查询的服务流程 |
| 任务可追踪 | 记录任务状态、文件状态、处理数量、错误信息和关键时间 |
| 增量处理 | 只对新增或发生变化的数据重新登记和处理 |
| 降低重复计算 | 超分辨模型在服务进程内按模型路径复用 |
| 降低存储风险 | 自动删除冗余中间文件，并定期清理历史任务目录 |
| 降低对接成本 | 将生产 RAW/XML 和超分辨算法限制在明确的模块边界内 |

具体节省的人力、平均处理时长、吞吐提升和资源利用率目前没有正式统计，均为**待确认**。

## 5. 整体架构

```mermaid
flowchart LR
    Client["调用方"] --> API["Flask API"]
    API --> Auth["API Key 认证与参数校验"]
    Auth --> Repository["TaskRepository"]
    Repository --> SQLite[("文件夹级 tasks.sqlite3")]
    Auth --> Worker["后台任务执行器"]

    Worker --> Sync["SyncService"]
    Sync --> Rsync["本机 rsync"]
    Rsync --> Folder["本地任务目录"]
    Sync --> RawService["Raw2BmpService"]
    RawService --> RawModule["raw2bmp 模块"]
    RawModule --> Folder
    Sync --> Repository

    Worker --> SR["SuperResolutionService"]
    SR --> ModelRunner["ModelRunner"]
    ModelRunner --> EP5["ep5_enhancement 模块"]
    EP5 --> Output["Super_Resolution 目录"]
    SR --> Repository

    Purge["PurgeScheduler"] --> Folder
    Purge --> Log["log/purge.log"]
```

### 5.1 接口层

`src/fa_server/app.py` 负责：

- 提供同步、更新同步、任务查询和超分辨接口。
- 对 `/api/v1/*` 接口执行 API Key 校验。
- 兼容 Windows 和 Linux 路径输入。
- 提供 `/health`、`/openapi.json` 和 `/docs`。

### 5.2 任务编排层

`src/fa_server/worker.py` 使用后台线程池执行长时间任务，使 HTTP 请求在完成任务登记后立即返回 `job_id`，调用方通过查询接口获取后续状态。

### 5.3 业务服务层

| 模块 | 主要职责 |
| --- | --- |
| `sync_service.py` | rsync 调用、文件发现、同步轮询、完成判断和文件生命周期管理 |
| `raw2bmp_service.py` | 管理单次 RAW 任务会话、加载 XML 配置、调用 RAW 处理模块 |
| `super_resolution_service.py` | 模型复用、增量扫描、批次处理和超分辨状态更新 |
| `purge_service.py` | 启动检查、定期检查、旧目录清理和清理日志 |

### 5.4 算法对接层

`src/raw2bmp/` 和 `src/ep5_enhancement/` 是生产代码的主要对接边界。业务服务依赖其对外方法，不直接访问算法内部实现，从而降低替换生产保密代码时对 API 和任务流程的影响。

### 5.5 持久化层

每个业务文件夹维护独立数据库：

```text
<local_root>/<folder_name>/tasks.sqlite3
```

主要数据表包括：

| 数据表 | 作用 |
| --- | --- |
| `sync_jobs` | 保存同步任务、完成状态、同步数量和错误信息 |
| `sr_jobs` | 保存超分辨任务、模型路径、批次配置和处理数量 |
| `image_tasks` | 保存每张输入图片的转换状态、超分辨状态及相关路径 |

SQLite 使用 WAL、事务和忙等待配置，任务创建时通过 `BEGIN IMMEDIATE` 检查同一文件夹的活跃任务，降低重复任务并发创建风险。

## 6. 端到端业务流程

### 6.1 同步任务

```mermaid
flowchart TD
    Start["提交同步任务"] --> Validate["校验 folder_name 与请求参数"]
    Validate --> Create["事务创建 sync_job"]
    Create --> Running["后台任务进入 running"]
    Running --> Pull["执行一次 rsync"]
    Pull --> Missing{"远端目录是否存在"}
    Missing -- "暂未创建" --> Wait["等待下一轮"]
    Missing -- "存在" --> Clean["清理 tmp 和冗余中间文件"]
    Clean --> Discover["发现符合处理规则的数据文件"]
    Discover --> Register["写入或更新 image_tasks"]
    Register --> Convert{"是否启用转码重命名"}
    Convert -- "是" --> Raw["加载 XML 并处理 RAW"]
    Raw --> Final["记录真实最终 BMP 路径并清理源文件"]
    Convert -- "否" --> Pending["直接进入超分辨 pending"]
    Final --> Complete{"manifest 是否满足"}
    Pending --> Complete
    Complete -- "是" --> Done["同步任务 completed"]
    Complete -- "否" --> Timeout{"是否达到空闲超时"}
    Timeout -- "否" --> Wait
    Wait --> Pull
    Timeout -- "是且数量不足" --> Partial["partially_completed"]
    Timeout -- "是且数量满足或无清单" --> Done
```

关键业务逻辑：

- 初始同步任务对 `folder_name` 保持唯一。
- 已存在文件夹通过更新接口执行后续增量检查。
- 同一文件夹同时只允许存在一个活跃同步任务。
- 远端目录尚未创建时不判定为任务失败，而是继续等待。
- 开启转码后，只有 `.raw` 文件进入 RAW 处理流程。
- XML manifest 和最终 BMP 名称优先用于完成判断。
- 无法通过 manifest 完成时，以空闲超时作为保险机制。
- manifest 预计数量与实际同步数量不一致时，任务可结束为 `partially_completed`。

### 6.2 RAW 转 BMP 与重命名

单次同步任务只创建一个 `Raw2BmpTaskSession`：

1. 首次处理 RAW 前加载 XML 配置。
2. 后续文件复用同一份配置。
3. 每个 RAW 文件调用生产模块的单文件处理方法。
4. 以生产模块返回的真实 `output_path` 作为最终产物。
5. 成功后更新 `sr_input_path`，使超分辨任务读取最终 BMP。
6. 删除 RAW、同名 BMP、`_converted.bmp`、`_convertedT.bmp` 等冗余文件。
7. 任务结束时统一输出处理成功和失败汇总。

该流程不再通过“原始名称加 T”等规则猜测生产输出路径。

### 6.3 超分辨任务

```mermaid
flowchart TD
    Start["提交超分辨任务"] --> Create["创建 sr_job"]
    Create --> Load["按 model_path 加载或复用模型"]
    Load --> Select["查询 pending 输入图片"]
    Select --> Batch{"是否形成可处理批次"}
    Batch -- "是" --> Processing["仅将当前批次标记 processing"]
    Processing --> Infer["传入输入图片绝对路径列表"]
    Infer --> Validate["校验返回成功数量或结果条目数"]
    Validate --> Record["按输入图片 ID 标记 done"]
    Record --> Progress["更新 processed_file_count"]
    Progress --> Select
    Batch -- "否" --> Complete{"同步已结束且无未完成图片"}
    Complete -- "是" --> Done["任务 completed"]
    Complete -- "否" --> Timeout{"是否达到空闲超时"}
    Timeout -- "否" --> Sleep["按间隔等待增量数据"]
    Sleep --> Select
    Timeout -- "是" --> Done
    Infer -- "异常" --> Failed["当前批次 failed，任务 failed"]
```

关键业务逻辑：

- 模型按绝对路径缓存，同一服务进程内不重复加载相同模型。
- 每次只领取一个批次，避免尚未推理的图片提前进入 `processing`。
- 每批完成后立即更新任务进度。
- 支持整数成功数、等长路径列表和包含 `None` 的等长结果列表。
- 超分辨处理记录以输入图片为准，不依赖生产输出文件名。
- 当前批次失败时，未进入本批次的图片继续保持 `pending`。
- 同步任务仍在运行时，超分辨任务继续等待增量数据。

### 6.4 数据清理

Purge 服务启动时执行一次检查，之后默认每 86,400 秒执行一次：

1. 按目录修改时间从旧到新排序。
2. 当任务目录超过默认保留数量 10 时，从最旧目录开始处理。
3. 存在 `queued` 或 `running` 任务的目录不删除。
4. 删除动作限定在配置的 `local_root` 内。
5. 日志记录扫描数量、清理数量、具体文件夹、跳过项和错误。

## 7. 关键状态设计

### 7.1 同步任务状态

| 状态 | 含义 |
| --- | --- |
| `queued` | 已登记，等待后台执行 |
| `running` | 正在同步和处理数据 |
| `completed` | manifest 已满足，或空闲超时后数量符合预期 |
| `partially_completed` | 任务已结束，但实际数量低于 manifest 预计数量 |
| `failed` | rsync、文件处理或服务执行发生未恢复异常 |

### 7.2 图片超分辨状态

| 状态 | 含义 |
| --- | --- |
| `pending_conversion` | RAW 尚未完成转换和重命名 |
| `blocked` | RAW 转换失败，暂不能进入超分辨 |
| `pending` | 输入图片已准备完成，等待超分辨 |
| `processing` | 当前批次正在推理 |
| `done` | 已按输入图片记录处理完成 |
| `failed` | 当前图片所在批次处理失败 |

## 10. 问题、风险与解决思路

| 优先级 | 问题或风险 | 影响 | 解决思路 |
| --- | --- | --- | --- |
| 高 | 真实 RAW/XML 和 Unet 代码尚未最终验证 | 可能出现格式、命名、颜色或输出契约差异 | 固定适配接口，使用生产样本建立验收数据集 |
| 高 | 服务异常退出后缺少自动恢复 | SQLite 可能残留 `running` 或 `processing` | 启动时扫描异常状态，根据更新时间重置或接管 |
| 高 | 当前使用 Flask Debug/Werkzeug | 不适合作为正式生产服务 | 关闭 Debug，接入 Waitress、Gunicorn 或统一进程管理 |
| 中 | `raw_extensions` 只限制本地发现，不限制 rsync 网络传输 | 不符合后缀的文件仍可能被下载 | 增加 rsync `include/exclude` 规则并补充联调测试 |
| 中 | 超分辨失败重试依赖重置脚本 | 无法精确只重试失败图片 | 增加按任务或状态恢复 `failed/processing -> pending` 的机制 |
| 中 | 关闭转码时 manifest 完成判断仍偏向最终 BMP | 可能只能等待空闲超时结束 | 根据转码开关分别检查 RAW 或最终 BMP |
| 中 | 同一文件夹超分辨冲突的接口异常映射需完善 | 可能返回非预期的服务器错误 | 将 `ActiveJobExists` 统一映射为 HTTP 409 |
| 中 | API Key 为单一静态密钥 | 密钥轮换和权限隔离能力有限 | 通过环境变量管理密钥，并规划轮换、HTTPS 和审计策略 |
| 低 | API 和任务日志尚未统一 | 跨模块排查需要组合多个日志来源 | 增加包含 `job_id`、`folder_name`、批次和耗时的结构化日志 |

生产数据规模、单任务文件数、目标时延、GPU 配置、并发量和磁盘容量阈值均为**待确认**，确认后才能给出准确的容量和性能方案。
